Where a model of brake tests can be trusted, and which tests to run next

The problem

Every new brake design has to be tested on a rig, and that takes time. A model that predicts the test result would save tests, but only where it can be trusted, and nobody knew where that was.

Role
Led the analysis
Lab
ADOPT Lab, IIT Madras
Client
Brakes India, part of the TVS Group, Chennai
Parts
Brake calipers and master cylinders

The idea

Build the models, then hold out whole groups of similar designs to find exactly where they fail. Those gaps become a plan for the tests worth running next.

1The company

Brakes India is part of the TVS Group in Chennai and one of the country's largest makers of brake systems, supplying brakes for cars, commercial vehicles and tractors. Every caliper and master cylinder it designs goes through hydraulic tests on a rig: how the part responds as pressure builds, how far it moves, and how much it rattles.

2Background

A new design is a new combination of clearances, dimensions, materials and test conditions. Building and testing each one takes time, so the engineers wanted a model that predicts the test result from the design. The catch is that a model is only good where it has seen data, and nobody knew where that was.

3What I built

Six test outcomes. We modelled four pressure-response characteristics of the master cylinder, a displacement characteristic of the caliper, and caliper rattle noise. Each design is described by its geometry, its material and specification category, and the test conditions.

Many models, compared fairly. Random Forest, gradient boosting, XGBoost, support-vector and nearest-neighbour regression, linear models and small neural networks. SHAP and permutation importance, checked against each other, showed which inputs actually moved each result.

The honest test. A random train/test split looked excellent: the best models reached an R² of about 0.94 to 0.96. But a random split puts near-identical designs on both sides. So I clustered the designs by their inputs alone with K-Means, then held out one whole cluster at a time, and also one whole specification or size class at a time. Under that test most targets generalised poorly, with R² below 0.5 and often negative. That is the real answer for a new design that does not look like the old ones.

0.94–0.96R² on a random split, which overstates what the model knows
< 0.5R² for most targets when a whole cluster of designs is held out

Where the data runs out. For each cluster I compared how much of every parameter's range had been tested and mapped the sparse regions. A cluster where the model failed almost always had narrow or thin coverage.

Reading the parameter space. For the targets where the model did hold up, I implemented the interpretable self-organising map (iSOM) method of Thole and Ramu. It lays all designs on a 2D grid of similar cells, and colours the same grid by the response and by each parameter, so an engineer can see which parameters drive the result, which hardly matter, and where the high-response zones sit.

Checked on real machines. For the caliper displacement, a balanced set of new tests was run on two production test machines. A small correction model, calibrated with a few measured points, brought the prediction on held-out pressure levels to an R² of about 0.96 on the second machine.

What the project delivered.

The lesson I took from it: a high accuracy number on a random split can hide a model that fails on the next new design. Telling the engineers exactly where the model cannot be trusted, and what data would fix that, was more useful than the number.
